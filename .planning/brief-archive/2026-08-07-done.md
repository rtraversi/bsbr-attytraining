### `ix-enrollorder` · Terminal

**Verbatim, as it stood on the board:**

> LATENT BUG terminal found while working elsewhere, not yet fixed. app/dashboard/page.tsx reads
> enrollments with NO ORDER BY and collapses them with Object.fromEntries. Migration 0007 dropped the
> unique constraint, so a RENEWED firm has multiple enrollment rows per user — the map then silently
> keeps an arbitrary one and the admin dashboard becomes NON-DETERMINISTIC after the first renewal.
> Every other read site orders by enrolled_at DESC. ⚠ RELATED AND ALREADY ON RECORD: 0007's own
> comment says reads order by created_at, which is not a column on the enrollments table — that exact
> mistake is documented from a prior session and this comment perpetuates it. Fix both together.

**Closed by `95c040e` (2026-08-05), "fix(dashboard): resolve each member to their current term, not
an arbitrary one".** Both halves, which is why it retires cleanly:

- `app/dashboard/page.tsx:63` now reads `.order('enrolled_at', { ascending: false })`.
- `Object.fromEntries` is gone, replaced by a `firstPerUser` helper that keeps the FIRST row per user
  rather than the last. The commit's own comment records why the original was worse than unordered:
  `fromEntries` keeps the last entry for a repeated key, so on a newest-first read it would have
  picked the OLDEST row — showing a member as "Expired" from last year's certificate the day after
  they recertified.
- The stale `0007` comment was corrected in the same change. Lines 7–27 of the migration now state
  explicitly that `created_at` is **not** a column on this table and that the timestamp is
  `enrolled_at`.

### `ix-multialert` · Terminal

**Verbatim, as it stood on the board:**

> Max chose to send operator alerts to BOTH solarsaiko@gmail.com and info@iurixaccreditation.com while
> the Zoho setup settles, and THE CODE CANNOT DO IT. lib/resend.ts types `to` as a bare string and
> passes it straight into Resend's JSON body; Resend accepts a string OR an array, but a single string
> containing a comma reads as one malformed address and fails. Setting the secret to a comma-separated
> value would have silently broken every alert — the exact failure fixed on 08-03. Interim: the
> cert-worker secret is the Gmail alone, which is known to work. Fix is to split on comma and pass an
> array, in lib/resend.ts and the cert-worker equivalent.

**Closed by `c1fdf67` (2026-08-04), "feat(email): let OPERATOR_ALERT_EMAIL hold more than one
address".** Both required locations, exactly as the item specified:

- `lib/resend.ts:37` exports `parseRecipients(to: string): string[]`, splitting on comma; `:57` calls
  it and `:69` passes the resulting **array** into the Resend body.
- `workers/cert-worker/src/index.ts:178` carries the same function. The comment at `:170` records that
  this is a **deliberate duplicate rather than a shared import**, because the Worker does not import
  from `lib/`.

⚠ The operational half is a separate question and is **not** closed by this: whether
`OPERATOR_ALERT_EMAIL` has actually been *set* to both addresses on both Workers. The code can now
carry a list; whether it currently does is a secrets question, and the cert-worker secret was last
recorded as the Gmail alone. That belongs with the cutover secret work, not here.
