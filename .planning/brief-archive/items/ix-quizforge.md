ORIGINAL REPORT FOLLOWS, kept verbatim as the record. 🔴🔴 CRITICAL — AN ENROLLED EMPLOYEE CAN SELF-CERTIFY IN ONE REQUEST. Found by terminal 2026-08-06, verified independently by desktop, NOT FIXED. app/api/quiz/attempt/route.ts takes the question IDs from the CLIENT (:96), fetches only those (:105), and computes score as correct / questions.length (:125) — the count the client chose to send, not the count it was served. Validation rejects only an empty array. POST a single answer you know is right and the score is 100%, passed is true, and a real certificate is generated and emailed. With unlimited retakes one question can be brute-forced in at most four attempts. It is authenticated and seat-gated, so the attacker is an enrolled employee holding a paid seat — precisely the person a Rule 5.3 product exists to hold accountable, and the certificate is the artefact the whole product sells. ✅ PARTIAL MITIGATION, forensic only: quiz_attempts stores the submitted answers array, so a forged pass is visible afterwards as an attempt containing one answer. Nothing surfaces or alerts on that. THE FIX: the server must decide which questions an attempt contains and score against THAT set, rejecting a submission that does not match. Needs the served-set recording described in ix-quizsubset, so the two are one piece of work. 🔴 THIS BLOCKS LAUNCH INDEPENDENTLY OF ix-stripeaudit. ✅ 2026-08-07: TODAY'S PRIMARY. Fix shape agreed and handed to terminal. New migration 0024 adds a quiz_sessions table (user, firm, course, question_ids, issued_at, expires_at, consumed_at) plus question_ids on quiz_attempts, which today has answers jsonb and nothing recording what was served. New route /api/quiz/start does the auth and seat gate, selects the set server-side, and returns sessionId plus questions carrying NO correct_index.
